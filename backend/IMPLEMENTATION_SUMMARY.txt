================================================================================
                         CORE FEATURES
================================================================================

1. REQUEST VALIDATION (TripRequest Model)
   ─────────────────────────────────────
   - Destination (non-empty string)
   - Days (1-365)
   - Travelers (1-50)
   - Budget (positive float)
   - Interests (1-20 items, deduplicated)
   - Max daily travel time (30-1440 min, default 180)
   
   All fields validated with Pydantic


2. COST CALCULATION (BudgetEngine)
   ──────────────────────────────
   Pure Python deterministic arithmetic (NO LLM):
   
   - Meal costs: $60/day/person (configurable)
   - Accommodation: $100/night/person (configurable)
   - Transportation: $20/day/person (configurable)
   - Activity costs: Per-activity customizable
   - Contingency fund: 10% of subtotal
   - Total cost breakdown
   - Budget validation with percentage used


3. ITINERARY EVALUATION (EvaluationService)
   ───────────────────────────────────────
   Multi-dimensional scoring:
   
   a) Budget Score (0-100)
      - 100: Cost ≤ 80% of budget
      - 85: Cost 80-90% of budget
      - 70: Cost 90-100% of budget
      - 50: Cost 100-110% of budget
      - 0: Cost > 110% of budget
   
   b) Preference Score (0-100)
      - Based on activity/interest matching
      - Scale: 0-20%, 20-40%, 40-60%, 60-80%, 80%+
   
   c) Activity Diversity Score (0-100)
      - Based on unique categories and activity density
      - Target: 3-5 activities/day, 4-6 unique categories
   
   d) Weather Score (Placeholder, 0-100)
      - Future: Weather API integration
   
   e) Travel Efficiency Score (Placeholder, 0-100)
      - Future: Route optimization
   
   Weighted Overall Score:
   - Budget: 30% | Preferences: 25% | Weather: 20% | 
     Travel Efficiency: 15% | Activity Diversity: 10%
   
   Replanning Logic:
   - Replan if overall score < 50, OR
   - Budget score < 30, OR
   - Preference score < 40


4. REST API ENDPOINTS
   ──────────────────
   
   a) GET /
      └─ Root endpoint with navigation
   
   b) GET /health
      └─ Health check (includes database status)
      └─ Response: {status, application, version, database}
   
   c) POST /api/trips/validate
      └─ Validate trip and get analysis
      └─ Input: TripRequest JSON
      └─ Output: {success, message, trip_details, budget_analysis,
                   cost_breakdown, evaluation_scores, recommendations}


5. CONFIGURATION MANAGEMENT (Settings)
   ──────────────────────────────────
   - Environment-based (loads from .env)
   - Optional API keys (won't fail if empty)
   - Sensible defaults
   - Type-safe with Pydantic


6. DATABASE INTEGRATION
   ────────────────────
   - MongoDB connection (optional)
   - Singleton pattern
   - Collections: users, trips, itineraries
   - Graceful offline fallback (app works without MongoDB)
   - Connection pooling with timeouts

================================================================================
                    IMPORT ARCHITECTURE
================================================================================

Circular Import Prevention:
  - app.config → No internal imports (base)
  - app.models → Only from pydantic (isolated)
  - app.services → From models only (unidirectional)
  - app.database → From config only (unidirectional)
  - app.main → All above (top level)

This prevents circular dependencies and ensures clean layering.

Common Issues & Solutions:

1. ModuleNotFoundError: No module named 'app'
   → Solution: cd backend (must run from backend directory)

2. MongoDB connection failed
   → Expected! App works offline. Just warnings in logs.

3. .env file not being read
   → Check: File must be at backend/.env (not backend/app/.env)
   → Format: KEY=value (no quotes, no spaces around =)

4. Pydantic validation errors
   → Check: All required fields provided, correct types
   → Reference: TripRequest model documentation

5. Port 8000 already in use
   → Solution: uvicorn app.main:app --reload --port 8001

   → Fix: Verify all ClassVar imports in evaluation.py

================================================================================
                    KEY DESIGN DECISIONS
================================================================================

1. No Circular Imports
   Why: Prevents bugs and makes testing easier
   How: Strict import hierarchy (config → models → services → main)

2. Deterministic Calculations (No LLM)
   Why: Arithmetic should be fast and predictable
   How: Pure Python with configurable constants

3. Graceful Database Fallback
   Why: Allows development without MongoDB setup
   How: Singleton with offline mode, no requirement on startup

4. Pydantic for Everything
   Why: Single source of truth for data validation
   How: BaseModel for data, BaseSettings for config

5. Optional API Keys
   Why: Enables local development without setup burden
   How: Optional[str] fields with defaults

6. 10% Contingency Fund
   Why: Real-world trip planning needs buffer
   How: Automatic 10% of subtotal added

7. Multi-Dimensional Evaluation
   Why: Single score ignores important factors
   How: Five dimensions with weighted combination

8. Fixed Weights (Not Learnable)
   Why: Interpretable for interviews and debugging
   How: ClassVar dictionary in EvaluationScore


================================================================================
                    INTERVIEW TALKING POINTS
================================================================================

Architecture & Design:
  "The backend uses a layered architecture with clear separation of concerns:
   config → database → models → services → main API. This prevents circular
   dependencies and makes testing each layer independently possible."

Validation:
  "We use Pydantic for all input validation, which provides both runtime
   checking and type hints for IDE support. Custom validators handle business
   logic like ensuring interests are deduplicated."

Cost Calculation:
  "Costs are calculated using pure Python with configurable defaults. We
   avoid calling LLMs for arithmetic since it's slow, expensive, and
   unreliable. The engine breaks down costs into meal, accommodation,
   transportation, and activity categories."

Evaluation Scoring:
  "We score itineraries across five dimensions: budget (30%), preferences
   (25%), activity diversity (10%), weather (20%), and travel efficiency
   (15%). Each dimension is independently calculable and scored 0-100."

Error Handling:
  "The app gracefully handles missing dependencies like MongoDB. If the
   database isn't available, the API still works - it just won't persist
   data. This is achieved through a singleton pattern with status checking."

Environment Management:
  "Configuration is entirely environment-based using pydantic-settings.
   No secrets are hardcoded, and optional API keys don't cause failures
   if missing."
